# Аудит репозитория Text2SQL

Дата аудита: 22 июля 2026 года.

## 1. Краткое резюме

Репозиторий представляет собой заготовку учебного соревнования по преобразованию русскоязычных вопросов в SQL для пяти синтетических предметных областей. В нём есть DDL-схемы PostgreSQL, генераторы синтетических данных, 500 пар «вопрос — эталонный SQL», скрипт детерминированного разбиения и простой grader.

Это **не готовая Text2SQL-система**: кода модели, инференса, schema linking, выполнения SQL и полноценной оценки нет. Более того, текущая конкурсная упаковка скомпрометирована: приватные вопросы и ответы открыто включены в архив, исходные JSON содержат все эталонные SQL, а `grade.py` реализует только строгое текстовое совпадение и допускает манипуляцию дубликатами строк submission.

До разработки baseline набор нужно привести в исполнимое и непротиворечивое состояние: починить генераторы, проверить все gold-запросы на реально поднятых PostgreSQL-базах, пересоздать честный hidden split и исправить grader.

## 2. Назначение проекта

По `README.md` и `ASSIGNMENT.md`, задача — разработать систему Text2SQL, которая получает вопрос на русском языке и описание схемы конкретной реляционной БД, а возвращает SQL-запрос, отвечающий на вопрос.

Предполагаемые сценарии:

- обучение/настройка на доступных примерах;
- генерация SQL для неизвестных вопросов в тех же пяти доменах;
- оценка предсказаний по закрытым эталонным запросам;
- в документации также заявлена проверка результата выполнения SQL, но в коде она отсутствует.

Репозиторий содержит данные и инфраструктурные заготовки, но не содержит решения, которое нужно сдавать: отсутствуют `inference.py`, модель/LLM-адаптер, индекс примеров, schema linker, SQL validator, исполнитель запросов и воспроизводимый evaluation pipeline.

## 3. Вход и выход системы

### Заявленный интерфейс инференса

Вход:

- `question`: русскоязычная строка;
- `schema`: структурированная схема или путь к `schema.sql`;
- `db_path`: подключение/путь к БД для проверки выполнения (хотя схемы ориентированы на PostgreSQL, а не на файловую SQLite-БД);
- практически необходим, но явно не выделен: `domain`, чтобы выбрать одну из пяти схем.

Выход:

- `predicted_sql`: одна строка SQL в диалекте PostgreSQL.

### Фактический интерфейс оценки

`grade.py` не вызывает модель. Он принимает готовый CSV submission и CSV ответов:

```bash
python grade.py submission.csv [answers.csv]
```

Если второй путь не указан, используется `private/answers.csv`. Результат — одно число: доля нормализованных точных совпадений, либо `1e-10` вместо нуля/при любой ошибке.

## 4. Устройство датасета

### Исходный набор

В `databases/` находятся пять каталогов. Каждый содержит:

- `schema.sql` — PostgreSQL DDL;
- `generate_data.py` — русскоязычный генератор `data.sql`;
- `generate_data_en.py` — англоязычный вариант генератора;
- `questions.json` — 100 объектов с полями `id`, `question`, `gold_sql`.

Всего: 5 доменов × 100 вопросов = **500 примеров**. В каждом домене ID идут от 1 до 100. Поле `domain` отсутствует внутри JSON и выводится из имени каталога.

Формат примера:

```json
{
  "id": 1,
  "question": "...",
  "gold_sql": "SELECT ...;"
}
```

Набор синтетический: генераторы используют фиксированный seed и создают шаблонные сущности (`Товар_1`, `Клиент_1` и т. п.) и случайные факты преимущественно за 2020–2025 годы. Готового `data.sql` в архиве нет; его требуется сначала сгенерировать.

Есть 8 групп дословно повторяющихся вопросов и 7 групп дословно повторяющихся gold SQL. Часть повторов находится внутри одного домена, часть — между доменами. Это уменьшает фактическое разнообразие и создаёт близкие/идентичные шаблоны по обе стороны случайного split.

`databases.zip` дублирует часть содержимого внутри основного архива и не используется кодом подготовки.

## 5. Структура баз данных

Все пять `schema.sql` используют PostgreSQL-конструкции: `SERIAL`, внешние ключи через `REFERENCES`, `CHECK`, `DECIMAL`, `DATE`/`TIMESTAMP`. Gold SQL также ориентирован на PostgreSQL: в 131 из 500 запросов используется `EXTRACT`, встречаются `ILIKE`, `INTERVAL`, `CURRENT_DATE` и `NULLS ...`. Заявленная поддержка SQLite требует нетривиальной конвертации не только DDL, но и запросов; готового адаптера нет.

Фактически **каждая схема содержит ровно 20 таблиц**:

| Домен | Основные сущности | Таблиц по документации | Фактически |
|---|---|---:|---:|
| Торговая компания | категории, товары, цены, поставщики, закупки, продажи, остатки, возвраты, платежи, промоакции | 24 | 20 |
| Юридическая фирма | практики, суды, клиенты, юристы, дела, заседания, документы, трудозатраты, счета, договоры, платежи | 22 | 20 |
| Логистика | локации, транспорт, водители, клиенты, грузы, отправления, маршруты, рейсы, трекинг, счета, инциденты, топливо | 21 | 20 |
| Горнорудная компания | рудники, минералы, оборудование, сотрудники, добыча, переработка, контракты, отгрузки, безопасность, экология, затраты | 20 | 20 |
| Нефтедобывающая компания | регионы, месторождения, скважины, платформы, добыча, бурение, трубопроводы, хранение, продажи, затраты, безопасность | 21 | 20 |

Связи в основном заданы обычными внешними ключами. Схемы достаточно широкие для проверки joins и агрегаций, но генераторы заполняют не все таблицы:

- trading: не заполняется `return_items`;
- legal: не заполняются 7 таблиц (`support_staff`, `invoice_items`, `opposing_parties`, `contracts`, `offices`, `case_notes`, `conflict_checks`);
- logistics: не заполняются 6 таблиц (`route_legs`, `trip_shipments`, `pricing_zones`, `invoice_lines`, `warehouse_operations`, `customer_contracts`);
- mining: не заполняются 3 таблицы (`extraction_sites`, `training_attendance`, `environmental_monitoring`);
- oil: не заполняются `platform_wells` и `contractors`.

Запросы к таким таблицам будут возвращать пустые результаты. Это делает execution accuracy слабой: семантически неверные запросы могут случайно совпасть по пустому результату.

## 6. Public/private split

`prepare.py` выполняет для каждого домена отдельное детерминированное перемешивание с `SEED = 42` и берёт 50% примеров в public, остальные 50% — в private. Seed домена вычисляется как SHA-256 от строки `42:<domain>`. Порядок объектов в каждом split сохраняет исходный порядок, меняется только принадлежность.

Фактический состав:

| Домен | Public | Private |
|---|---:|---:|
| каждый из 5 доменов | 50 | 50 |
| всего | 250 | 250 |

ID public и private внутри домена не пересекаются и в объединении дают все 100 ID. Схемы и оба генератора побайтово одинаково копируются в оба split.

### Критическая проблема split

Это не закрытый тестовый набор:

1. В архиве присутствует `private/answers.csv` со всеми 250 закрытыми gold SQL.
2. В архиве присутствуют `private/databases/*/questions.json`, также содержащие вопрос и `gold_sql`.
3. В исходных `databases/*/questions.json` открыты все 500 вопросов и ответов.
4. Даже public JSON не удаляет `gold_sql` из учебных примеров (для train это допустимо), а private JSON также не удаляет его (для hidden test недопустимо).
5. Алгоритм split и фиксированный seed опубликованы, поэтому принадлежность можно воспроизвести.
6. `sample_submission.csv` перечисляет точные `(domain, id)` private-набора.

Таким образом, любая оценка на текущем private полностью утратила смысл: submission можно собрать прямым копированием `private/answers.csv`.

Кроме прямой утечки, случайный split вопросов внутри тех же схем и из тех же вручную созданных наборов не проверяет перенос на новые БД. Повторяющиеся и шаблонно близкие вопросы могут оказаться по разные стороны split.

## 7. Формат submission

`public/sample_submission.csv` содержит 250 строк — по одной для каждого private ID — и три колонки:

| Колонка | Тип по смыслу | Назначение |
|---|---|---|
| `domain` | строка | имя каталога домена, например `01_trading_company` |
| `id` | целое | ID вопроса внутри домена |
| `predicted_sql` | строка | предсказанный SQL |

Шаблон заполнен `SELECT 1`, чтобы pandas прочитал колонку как строковую. Ключом должна быть пара `(domain, id)`. CSV обязан корректно экранировать SQL с запятыми и кавычками.

Формат не несёт сам текст вопроса; он предполагает, что участнику отдельно доступен private test input. В текущей упаковке он доступен вместе с ответом, что и создаёт утечку.

## 8. Заявленные метрики

В документации перечислены:

1. **Execution Accuracy (EX)** — совпадение результатов выполнения predicted и gold SQL.
2. **Exact Match (EM)** — текстовое совпадение после нормализации.
3. **Jaccard Distance (JD)** — расстояние между множествами SQL-токенов.
4. **Latency** — средняя задержка инференса при batch size 1 на CPU.
5. **Valid SQL Rate (VSR)** — доля выполняющихся без ошибки запросов.
6. **Test Suite Accuracy (TSA)** — опциональная проверка на нескольких экземплярах данных той же схемы.

Заявленная итоговая формула:

```text
Score = 0.50 × EX
      + 0.20 × (1 - JaccardDistance)
      + 0.15 × VSR
      + 0.10 × EM
      - 0.05 × norm(Latency)
```

Для EX документация допускает сортировку результата по всем колонкам перед сравнением, но не определяет сравнение типов, `NULL`, floating point tolerance, дубликатов строк, порядка колонок и ошибок выполнения. Нормализация latency также не определена.

## 9. Что реально реализовано в `grade.py`

Реализована только одна метрика: **case-insensitive whitespace-normalized Exact Match**.

Нормализация:

```python
" ".join(str(sql).strip().lower().split())
```

Она приводит SQL к нижнему регистру, обрезает края и схлопывает любые пробельные последовательности. Она **не**:

- удаляет завершающую `;`;
- нормализует кавычки, алиасы, скобки или операторы;
- учитывает эквивалентный порядок условий;
- удаляет комментарии;
- парсит SQL;
- выполняет SQL.

`grade.py` не реализует EX, JD, latency, VSR, TSA и не вычисляет заявленный composite score. Возвращаемое число — `correct / len(merged)`. Нулевой результат и любая ошибка заменяются на `1e-10`, то есть функция вопреки документации фактически не возвращает точный ноль.

## 10. Ошибки, противоречия и уязвимости

### Критические

1. **Полная утечка private labels.** `private/answers.csv`, private JSON и полные исходные JSON опубликованы.
2. **Grader не соответствует заявленной оценке.** Итог соревнования фактически определяется только EM, хотя документация отводит EM 10%.
3. **Манипуляция дубликатами submission.** Перед merge grader не проверяет уникальность `(domain, id)`. Если многократно повторить несколько заведомо правильных строк, merge размножит их и они получат непропорционально большой вес; score можно приблизить к 1, не отвечая на большинство вопросов.
4. **Генератор legal не запускается.** Оба файла `02_legal_firm/generate_data.py` и `generate_data_en.py` содержат недопустимый вложенный f-string с экранированными кавычками и дают `SyntaxError` (русский — строка 39, английский — строка 55).

### Высокий приоритет

5. **Нет готовых БД и нет воспроизводимого one-command setup.** README предлагает один общий пример с БД `text2sql`, но пять схем содержат одинаковые имена таблиц (`customers`, `payments`, `employees` и т. п.); их нельзя без конфликтов загрузить подряд в одну schema PostgreSQL. Нужны отдельные базы или PostgreSQL schemas.
6. **Заявленное число таблиц неверно в четырёх доменах.** Фактически во всех доменах по 20 таблиц.
7. **Генераторы заполняют только 81 из 100 таблиц.** Девятнадцать таблиц остаются пустыми, хотя могут участвовать в вопросах.
8. **Нет проверки gold SQL.** В репозитории нет кода, который создаёт БД, запускает все 500 запросов и подтверждает их выполнимость/однозначность.
9. **SQLite заявлен как альтернатива, но не поддержан.** Нужна конвертация DDL и PostgreSQL-выражений в 500 gold SQL; простого списка замен из README недостаточно.
10. **EX на одном случайном датасете подвержена ложным совпадениям.** Особенно для пустых таблиц и редких фильтров. TSA только упомянута, но не реализована.

### Средний приоритет

11. **Проверка submission неполна.** Не проверяются точный набор ключей, дубликаты, лишние строки, порядок/названия всех колонок и тип содержимого до merge. Лишние ID молча игнорируются, пропущенные считаются неверными.
12. **Любая ошибка скрывается.** Широкий `except Exception` возвращает `1e-10`, не объясняя участнику причину неверного формата или внутренней ошибки.
13. **Нет безопасного выполнения SQL.** Для EX понадобятся read-only транзакции, statement timeout, запрет нескольких statements и DDL/DML, лимиты ресурсов.
14. **Неоднозначность документации.** Не определены точная версия PostgreSQL, способ адресации домена, правила сравнения result sets, схема нормализации latency и веса доменов.
15. **Повторы в вопросах/gold SQL.** Найдены 8 повторных групп вопросов и 7 повторных групп SQL; они искажают независимость примеров и могут пересекать split.
16. **Артефакты поставки.** В архив включён `__pycache__`, а также вложенный `databases.zip`; это не функциональная ошибка, но признак отсутствия чистой процедуры сборки релиза.

## 11. Что именно необходимо разработать

### Сначала — исправить benchmark

- единый скрипт создания пяти изолированных PostgreSQL databases/schemas;
- исправленные и проверенные генераторы данных;
- заполнение всех таблиц либо удаление/переосмысление вопросов к незаполненным таблицам;
- автоматическая проверка DDL, FK/constraints и всех gold SQL;
- новый private test, ответы которого никогда не попадают в public artifact;
- желательно split по шаблонам/сложности или по новым схемам, а не случайный split внутри одних 500 примеров;
- строгая схема submission и безопасный grader;
- реализация EX, EM, token similarity/Jaccard, VSR и, при необходимости, TSA/latency;
- формальная спецификация сравнения результатов.

### Затем — разработать Text2SQL baseline

- загрузчик вопросов и DDL;
- SQL/DDL parser и компактное представление схемы;
- schema linking: таблицы, колонки, значения и связи FK;
- retrieval похожих public примеров без доступа к private labels;
- генератор SQL (LLM или локальная seq2seq-модель) с PostgreSQL-инструкцией;
- синтаксическая валидация и ограничение запроса до одного read-only `SELECT`/`WITH`;
- execution-guided retry по диагностике PostgreSQL;
- CLI `inference.py` и batch-генератор submission;
- локальная оценка на честном validation split;
- логирование latency, ошибок и результатов по доменам/типам запросов;
- `requirements.txt`, конфигурация и инструкция воспроизводимого запуска.

## 12. Рекомендуемый план реализации baseline

### Этап 0. Санитарная подготовка данных

1. Починить legal generators и поднять отдельную PostgreSQL schema для каждого домена.
2. Сгенерировать данные фиксированно и проверить загрузку без нарушений constraints.
3. Выполнить каждый gold SQL; вручную разобрать ошибки и подозрительные пустые результаты.
4. Удалить текущий private из распространяемого пакета и создать новый hidden test.
5. Зафиксировать валидный train/dev split с группировкой одинаковых/похожих шаблонов.

Без этого любые цифры baseline недостоверны.

### Этап 1. Минимальный retrieval baseline

1. Нормализовать вопрос (lowercase, `ё/е`, числа/даты, лемматизация опционально).
2. Внутри соответствующего домена искать ближайший public вопрос через BM25 или sentence embeddings.
3. Использовать gold SQL ближайшего примера как template и аккуратно заменять явно распознанные даты, числа и строковые значения.
4. Это даст быстрый, дешёвый нижний ориентир и покажет степень шаблонности набора.

### Этап 2. LLM baseline со schema linking

1. Парсить DDL в список таблиц, колонок, PK/FK и типов.
2. По вопросу отбирать релевантные таблицы/колонки, сохраняя соединяющие FK-пути.
3. Добавлять 3–5 ближайших **только public/train** примеров того же домена.
4. Просить модель вернуть один PostgreSQL `SELECT` без Markdown и пояснений.
5. Использовать низкую temperature и детерминированные настройки.

### Этап 3. Валидация и execution-guided repair

1. Разбирать ответ SQL-парсером.
2. Запрещать DDL/DML, несколько statements и опасные функции.
3. Выполнять в read-only транзакции с коротким timeout.
4. При синтаксической ошибке, неизвестной таблице/колонке или неверном типе делать 1–2 repair-попытки с текстом ошибки и релевантной частью схемы.
5. Не подгонять запрос по совпадению с private gold/result.

### Этап 4. Оценка

1. Считать VSR и latency непосредственно во время инференса.
2. Считать EX с канонизацией result set, отдельно фиксируя ordered queries.
3. Считать EM и token Jaccard как диагностические, а не как замену EX.
4. Публиковать macro-average по пяти доменам и разрезы по сложности: single-table, joins, aggregation, nested query, date logic.
5. Для защиты от случайных совпадений прогонять запросы на нескольких независимо сгенерированных экземплярах данных.

## 14. Критерий готовности baseline

Baseline можно считать воспроизводимым, когда чистая среда одной командой создаёт пять БД, все gold SQL проходят проверку, private labels отсутствуют из доступного решения, инференс генерирует ровно одну строку на каждый test key, а evaluator прозрачно выдаёт EX/EM/Jaccard/VSR/latency по доменам и в целом. До выполнения этих условий оптимизировать модель преждевременно.
