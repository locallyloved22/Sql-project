# Text2SQL: краткий отчёт о решении

## 1. Задача и результат

Цель проекта — преобразовать вопрос пользователя на русском языке в корректный SQL-запрос для одной из пяти предметных баз: торговой, юридической, логистической, горнодобывающей или нефтяной. Система должна учитывать схему выбранной базы, не обращаться к несуществующим таблицам и колонкам, безопасно выполнить запрос и вернуть пользователю результат.

Реализован end-to-end пайплайн: вопрос → анализ схемы → подбор релевантных таблиц и few-shot примеров → генерация SQL языковой моделью → очистка и статическая проверка → выполнение в PostgreSQL → до двух попыток исправления → русский ответ и таблица. Для обычного пользователя сделано нативное desktop-окно, запускаемое на macOS двойным кликом по `START_TEXT2SQL.command` или готовой задачей VS Code. Браузерный интерфейс сохранён как дополнительный вариант.

## 2. Данные и окружение

Проект работает со всеми пятью предоставленными доменами. Воспроизводимое окружение поднимается через Docker Compose и содержит пять независимых экземпляров PostgreSQL 16. Во всех базах по 20 таблиц, всего загружается 566 671 синтетическая строка:

| Домен | Строк |
|---|---:|
| Торговая компания | 266 197 |
| Юридическая фирма | 66 613 |
| Логистика | 169 873 |
| Горнодобыча | 27 483 |
| Нефтедобыча | 36 505 |

Исходные генераторы данных не изменяются. Сборщик создаёт исправленные SQL-файлы отдельно: исправляет синтаксическую ошибку legal-generator и некорректный диапазон дат в trading-generator. Запросы приложения выполняются пользователем `text2sql_reader` в read-only транзакции со statement timeout. DDL и DML запрещены дополнительной AST-валидацией.

## 3. Архитектура

Схема разбирается из `schema.sql`: извлекаются таблицы, колонки, типы, первичные и внешние ключи. Schema linker оценивает соответствие слов вопроса названиям таблиц и колонок и оставляет наиболее релевантную часть схемы. Это уменьшает размер промпта и количество ложных ссылок на сущности.

Retriever выбирает несколько семантически близких public-примеров из того же домена. В prompt передаются правила PostgreSQL, отобранная схема, примеры и вопрос. Поддерживаются OpenAI-compatible API и Ollama. Для формально открытого решения рекомендуется Ollama с open-weight code-моделью. Mock-провайдер содержит только 15 фиксированных smoke fixtures и не считается моделью.

Ответ LLM очищается от Markdown и пояснений. `sqlglot` проверяет, что получен один `SELECT` или `WITH … SELECT`, нет операций изменения данных, а таблицы и колонки существуют. Затем SQL выполняется в PostgreSQL. При ошибке модель получает вопрос, схему, предыдущий SQL и сообщение PostgreSQL и может сделать до двух исправлений. Итоговый естественно-языковой ответ формируется только из реальных строк, поэтому formatter не выдумывает значения.

Основной пользовательский интерфейс сделан на Tkinter и не зависит от браузера. Дополнительно доступен Streamlit-вариант. Оба показывают готовность базы, предлагают примеры вопросов, позволяют выбрать модель и домен, отображают ответ, таблицу, SQL, latency, число исправлений и экспорт CSV. API-ключ, введённый в интерфейсе, живёт только в памяти процесса.

## 4. Оценка

`solution/evaluate.py` реализует public-оценку по всем требованиям задания:

- raw и normalized Exact Match;
- токеновый Jaccard similarity;
- Valid SQL Rate: запрос должен пройти AST-проверку и успешно выполниться;
- Execution Accuracy: результат predicted SQL сравнивается с полным результатом gold SQL;
- latency и количество коррекций;
- статистика по доменам, сложности и типам SQL;
- итоговая формула `0.50×EX + 0.20×Jaccard + 0.15×VSR + 0.10×EM − 0.05×normLatency` и средний FinalScore по пяти доменам.

Если в gold SQL есть `ORDER BY`, порядок строк учитывается; иначе результаты сортируются перед сравнением. Ошибка генерации, валидации или выполнения всегда даёт `EX = 0` и остаётся в общем знаменателе. Для точного leaderboard score можно передать общие границы latency параметрами `--latency-min-seconds` и `--latency-max-seconds`; без них применяется min-max текущего прогона и это явно отмечается в JSON.

Опциональная TSA не включена: для неё организатор должен предоставить несколько экземпляров данных той же схемы. Архитектура executor позволяет добавить их как дополнительные DSN без изменения генерации.

## 5. Проверки и результаты

Автоматические unit-тесты покрывают парсинг схемы, безопасность SQL, очистку ответа, метрики, полный знаменатель EX, итоговый score, конфигурацию, formatter и mock fixtures. Текущий результат — 18 успешно пройденных тестов.

Execution smoke suite содержит три запроса на каждый домен. Все 15 запросов прошли AST-валидацию, выполнились на реальных PostgreSQL-базах и вернули строки. Веб-интерфейс также проверен end-to-end на вопросе о пяти крупнейших покупателях: он сформировал SQL, получил пять реальных строк и показал их пользователю.

Предыдущий полный public-прогон mock дал почти стопроцентную техническую валидность, но `EX = 0`, что ожидаемо: mock не генерирует SQL для произвольных вопросов. Этот результат нельзя выдавать за качество настоящей модели. Для измерения итогового качества необходимо запустить evaluator с выбранной Ollama-моделью либо разрешённым API-провайдером.

## 6. Воспроизводимость и ограничения

Первый запуск выполняется `./setup.sh`; обычная работа — двойным кликом по `START_TEXT2SQL.command`, командой `./start_desktop.sh` или задачей VS Code. Setup устанавливает зависимости, строит данные, запускает контейнеры, проверяет 100 таблиц, выполняет unit и smoke tests. Submission создаётся в формате `domain,id,predicted_sql`; по умолчанию используется public split.

Исходный benchmark содержит противоречия: фактическое количество таблиц отличается от документации, private-материалы в архиве включают ответы, а часть вопросов и генераторов имеет дефекты. Эти проблемы подробно зафиксированы в `REPOSITORY_AUDIT.md`. Pipeline не использует private split для retrieval или оценки, однако исходный private split следует считать скомпрометированным и не использовать как доказательство обобщающей способности.

Главное оставшееся экспериментальное решение — выбор и настройка открытой LLM. Инфраструктура, пользовательское приложение, безопасное выполнение, evaluator и формат сдачи готовы и не зависят от конкретной модели.
